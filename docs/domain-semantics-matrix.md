# Domain semantics matrix — 16 October 2026

This specification distinguishes the meaning of a fact from whether a source requires it. No rule below invents a government requirement. Policy comparisons still require reviewed source/version evidence. Unknown answers, explicit No, a question that does not apply, and missing verification are different states.

The backend owns `profiles/semantics.json`; `make contracts` copies it to `semantics.generated.json`. Both implementations consume the same field references, predicates, EN/HI explanations and error/warning levels. Nineteen fictional cases in `data/fixtures/domain-semantic-cases.json` run through Python and the actual browser module. Eligibility uses independent closed typed comparisons, with explicit current-enrollment dependencies, not an LLM validator.

Test references: **S** = named shared case in `test_domain_semantics.py` and `common-sense.spec.ts`; **E** = focused evaluator tests in `test_domain_semantics.py`/`test_rules.py`; **P** = `test_profile_completion.py`; **W** = `test_workspaces.py`; **D** = `test_document_vault.py`; **R** = nine actual emulator/API/PostgreSQL/browser workflows in `common-sense.spec.ts` and `product-real.spec.ts`. These references identify concrete coverage, not independent test totals.

## Fact and relationship inventory

All fact values retain origin, verification and optional inclusive validity boundaries. Missing/null is unknown; Boolean false and numeric zero are explicit values. AI inference is not authoritative. Application-level validation is not an official eligibility decision.

| Fact(s) / relationship | Meaning and time | Allowed / invalid / ambiguous combinations; required clarification |
|---|---|---|
| `age` | Whole years 0–130, as recorded; explicit source as-of date respected | Negative/fractional/>130 rejected. No DOB field or automatic birthday advancement. Recorded date shown when available; undated legacy age needs confirmation, not a fabricated birth date. |
| `student_status` | Studying now within the stated interval | True/false/null distinct. Independent of employment and completed qualifications. Active mode/course with No needs dating/correction; unchanged legacy conflicts become visible warnings. |
| `current_education_level` | Current course/class, not awarded qualification | Requires contemporaneous enrollment for evaluation; school/UG/PG/other options including below IX. `none` is invalid here. No course rank/age assumption. |
| `highest_completed_education` | Highest qualification actually completed | Does not establish current study; explicit none valid. No automatic completion from a current course. |
| `education_level` | Preserved legacy education answer with unclear meaning | Never silently migrated to attainment/current study. Its old source rule is unknown until an administrator clarifies meaning. Separate user answers can be added without deleting it. |
| `enrollment_mode` | Current full-time/part-time/distance mode in its interval | Nonstudent same active period needs correction; historical mode can coexist. Full-time job plus part-time course valid. |
| `school_recognized_or_government` | Current school status, not every institution ever attended | Shown for current school classes; evaluation needs current enrollment/school course. University course plus historical school is valid, not current school evidence. |
| `employment_status` | Current work situation | Employed/unemployed/self-employed does not imply education, income amount, registration or benefit qualification. No protected-fact manipulation suggested. |
| `nationality` | Nationality, independent of location | Supported Indian aliases normalized for comparison; Other is ambiguous. Non-Indian naming/code/dual-nationality breadth is limited; source wording must be clarified rather than universal legal claims. |
| `domicile_state`, `domicile_district` | Scheme-relevant domicile, not current residence | Can differ from residence. No automatically assumed domicile based on discovery filter or business address. Scheme-specific proof remains separate. |
| `residence_state`, `residence_district` | Current residence for a person; legacy operating location within a business subject | Context determines dimension; never copy between subject kinds. Registration location has distinct business keys. No lifetime location assumption beyond saved validity. |
| `annual_personal_income`, `annual_parental_income` | Amount for exact declared definition and period | Nonnegative including zero; missing period/basis allowed to save but not compare. Parental ≠ personal ≠ automatically summed household income. One editable scope per key; simultaneous complex scopes remain a limitation. |
| `disability_percentage` | Recorded percentage, 0–100, not authenticity | Independent of uploaded certificate; percentage cannot establish verification or all scheme-specific category semantics. Negative/>100 rejected. |
| `has_income_certificate`, `has_disability_certificate`, `has_udid_certificate`, `has_registration_certificate` | Legacy self-reported possession or separately verified evidence | UI directs to vault rather than setting verification. Self-reported true/false does not satisfy an authoritative documentary condition. Uploaded ≠ verified; stored verified facts remain protected. |
| `has_bank_account`, `auto_debit_consent` | Separate self-reported banking fact and affirmative permission | Neither implies the other. No actual bank debit/action is performed; missing consent is not silently granted. No new forced onboarding fields. |
| `business_registered` | Explicit business registration answer, with source-specific registry still requiring interpretation | Does not derive from legal structure/owner employment/certificate upload. No invented GST/Udyam identity. |
| `business_turnover` | Business receipts for exact period/basis | Not personal income; zero valid, no history unknown. Dates survive unrelated business edits; scoped evaluation does not mix periods. |
| `business_registration_state`, `business_registration_district` | Registration location, distinct from operation | Optional and independent; absence not inferred from operation. Specific legal registration constraints remain source-backed. |
| `business_operating_status` | Active/inactive/prelaunch/null at the declared time | Legal structure/registration do not imply operating. Inactivity is a blocker only if a reviewed rule requires activity. |
| Household membership | Dated association, not automatic lifetime family identity/access | Only active memberships shown. Cannot imply parental income definition or consent. Historical people/relationships retained. |
| Guardian relationship + ConsentGrant | Active explicit guardian assertion plus unrevoked/unexpired scope | Both required; future/ended relationship cannot grant current access. Existing future-guardianship check retained. No adult access merely from kinship; invitation workflow remains deferred. |
| Business membership | Owner/admin/editor/viewer server-side role | Viewer reads authorized business documents but cannot mutate; removed membership loses access. Owner personal facts remain separate. |
| DocumentRequirementLink | Explicit permitted use against immutable published requirement/version and compatibility | Filename/hash alone does not merge scopes/owners. Income period, definition, policy/issuer/format constraints retained; newer rule version needs fresh suitability review. |
| ActionItem | User task progress, not factual or legal proof | Pending/in-progress independent from file absent/uploaded/expired and legal satisfied/unknown/unsatisfied. No automatic verified/completed government status. |

Unmodeled complexity stays explicit: multiple concurrent courses, DOB-based age calculation, multiple editable parallel income scopes, full adult-consent invitation UI, authoritative document verification and account erasure/export. These limitations must not be “fixed” by inventing facts or source policy.

Location-language regression: Rajasthan/राजस्थान, Dausa/दौसा, Delhi/दिल्ली, Maharashtra/महाराष्ट्र and Pune/पुणे are representation aliases within the **same** fact dimension. Unmapped cross-language names remain unknown pending clarification, never a guessed domicile or automatically transferred registration address. `test_location_language_aliases_do_not_mix_residence_domicile_or_registration` covers matching and separation.
